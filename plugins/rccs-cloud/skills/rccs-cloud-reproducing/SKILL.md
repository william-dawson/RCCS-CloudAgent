# Turning a session into a reproducible notebook

A chat transcript is not something a co-author (or you, in six months) can
re-run. This skill distills what actually mattered out of an interactive
session into a linear Jupyter notebook that calls the *same* MCP tool surface
you've been using — `cloud_mcp.hpc_server` via `hpc_agent_core.client` — not a
hand-copied `ssh`/`scp` script. See `hpc-agent-core`'s
[`PORTING.md` §12](https://github.com/william-dawson/hpc-agent-core/blob/main/PORTING.md)
for the full rationale and contract; this skill is the R-CCS-Cloud-specific
walkthrough of applying it.

`examples/reproduction_demo.ipynb` in this repo is a real, worked example —
imitate its structure (markdown beat, code cell, repeat) rather than starting
from a blank notebook.

## Workflow

1. **Re-derive the narrative, don't transcribe the chat.** Figure out what
   the user's actual question/result was, and the minimal sequence of tool
   calls that produces it — cut the dead ends, the wrong partition you tried
   first, the debugging detours. Those can get one honest sentence in
   markdown ("genoa was saturated, so this ran on fx700 instead") if they're
   informative, but the notebook's code should be the clean path, not a
   replay of every false start.

2. **Structure**: markdown cell explaining the next step, immediately
   followed by the code cell that does it. Start with:

   ```python
   from hpc_agent_core.client import connect_sync, dev_params

   CACHE_DIR = "./.hpc_cache/<name>"
   hpc = connect_sync(dev_params("cloud_mcp", "hpc_server"), mode="lazy", cache_dir=CACHE_DIR)
   ```

   Use `connect_sync`, not the async `connect()` — no `await`, no manual
   `__aenter__`/`__aexit__` spread across cells; a domain scientist reading
   this shouldn't need to know it's backed by asyncio at all.

3. **Never author a cell's output.** Actually execute the notebook's code
   (as a plain script is fine for this step — the point is real execution,
   not the `.ipynb` format specifically) against the real cluster, capture
   the real stdout/return values, and only then write them into the
   notebook's `outputs`. Two real bugs in the underlying caching machinery
   were only caught this way, not by reading the code — see PORTING.md §12
   for both. Treat "run it for real" as non-negotiable, not a nice-to-have.

4. **Validate with `mode="live"` from a clean state** before calling it
   done — a fresh job submission, a fresh poll, a fresh download. Only
   after that succeeds, seed `examples/.hpc_cache/<name>/` from the real
   cache directory it just wrote (copy the `.json` files and any `.blob`
   files for cached downloads) and commit it alongside the notebook. That
   seeded cache is what lets `mode="replay"` reproduce the whole notebook
   for someone with no cluster account — prove this by actually running
   the notebook's assembled code from an isolated directory containing only
   that seeded cache before considering it done.

5. **Add the notebook's runtime download directory to `.gitignore`**
   (e.g. `examples/downloads/`) — it's regenerated by running the notebook,
   not part of what gets committed. The `.hpc_cache/<name>/` directory itself
   *is* committed — that's the recording, not scratch output.

6. If the job spec needs a partition choice and it's not obvious which one,
   check `get_resources`/`sinfo` for idle capacity first (see
   `rccs-cloud-monitoring-jobs`) rather than defaulting to `genoa` — it's the
   default partition but not always the least busy one, and a demo notebook
   sitting `PENDING` for a long time is a bad first impression.
